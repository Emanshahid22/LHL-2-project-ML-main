# LER-1136 — Access log immutability

_UC-07 Sensitive Material Handling · epic: `docs/usecases/uc-07/epic.md` · PRD: `docs/usecases/uc-07/prd.md`_

_Client ticket **LER-1136** (Story, To Do) · delivering ticket: **LER-1250** · build order: story 11 of 15, stage 3._

## User Story
As a compliance-minded practice, we want access records that nobody can edit or delete, so that the trail is defensible under later challenge.

## Acceptance Criteria
- Given the whole API surface, when it ships, then no route and no service method updates or deletes an `AuditEvent` or a `SensitiveAcknowledgement` — creation is the only verb.
- Given the suite, when immutability is proven, then a structural check greps `apps/api/src` (comments stripped) for `auditEvent.update`, `auditEvent.delete`, `auditEvent.deleteMany`, `auditEvent.updateMany` and the acknowledgement equivalents, and fails on any hit.
- Given prior audit rows for a draft, when subsequent operations of any kind run against that draft, then the earlier rows still read back byte-identical.

## Notes & Constraints
- E2E hygiene is the one legitimate deleter and it operates directly on the throwaway/dev database via
  Prisma in the test harness — never through the API. The structural check scopes to `apps/api/src` for
  exactly this reason.
- "By anyone" includes future code: the structural check is the regression guard, which is why it greps
  source rather than probing routes that do not exist today.

## Definition of Done
- Delivered against the acceptance criteria above
- `npm run test:e2e` green and both builds pass
- `npm run conformance` and `npm run orphan-scan` pass
- Every existing `data-testid` intact
- Test drafts cleaned from `apps/api/prisma/dev.db`

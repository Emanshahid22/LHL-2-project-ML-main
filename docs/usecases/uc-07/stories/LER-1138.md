# LER-1138 — Locked section for users without the permission

_UC-07 Sensitive Material Handling · epic: `docs/usecases/uc-07/epic.md` · PRD: `docs/usecases/uc-07/prd.md`_

_Client ticket **LER-1138** (Story, To Do) · delivering ticket: **LER-1252** · build order: story 13 of 15, stage 1._

## User Story
As a firm, we want colleagues without sensitive-material access to see that a sensitive section exists without ever receiving its content, so that access control is a server fact rather than a client courtesy.

## Acceptance Criteria
- Given a draft owner WITHOUT the permission and an active section, when they open the form, then the section renders locked: red banner, lock explanation — and no MG6D field, instruction text or PII content anywhere in the DOM.
- Given the network, when that user fetches the draft (list, single, PATCH response, autofill response), then sensitive-declared values are absent from the payload — redacted server-side, not hidden.
- Given that user keeps working on the rest of MG6, when autosave fires, then the save succeeds and the stored sensitive values are untouched (merge-preserve, open-questions F1) — being locked out must never mean destroying what others wrote.
- Given the derived flag, when redaction is applied, then `hasSensitiveMaterial` and the `sensitiveSection` block (active/permitted/level/holders) survive — the locked user must know the section exists and how to get access.
- Given a user without the permission, when they attempt the confirmation endpoint or a sensitive-touching PATCH directly, then 403 + `SENSITIVE_ACCESS_DENIED` (LER-1131's guard).

## Notes & Constraints
- The permission is `sensitiveMaterialAccess` on the demo `User` (additive migration; PRD §5). Seed:
  demo user true, colleague false — the E2E flips actors with the existing `x-user-email` override.
- "Content is never sent to an unauthorised client" is the client ticket's own line and the whole point:
  test the PAYLOAD, not the CSS.

# LER-1134 — Sensitive items excluded from the non-sensitive schedule export

_UC-07 Sensitive Material Handling · epic: `docs/usecases/uc-07/epic.md` · PRD: `docs/usecases/uc-07/prd.md`_

_Client ticket **LER-1134** (Story, To Do) · delivering ticket: **LER-1248** · build order: story 09 of 15, stage 3._

## User Story
As a defence solicitor, I want the non-sensitive schedule export to be incapable of containing sensitive items, so that disclosure through the wrong document cannot happen by my mistake.

## Acceptance Criteria
- Given no export existed before UC-07 (open-questions F3), when this story ships, then `GET /drafts/:id/export/non-sensitive-schedule` returns the unused-material schedule as a CSV attachment, built by ONE shared function (`buildNonSensitiveScheduleCsv`) both the endpoint and the tests call.
- Given a schedule holding sensitive and non-sensitive rows, when the export is generated, then rows whose classification is sensitive are absent and MG6D fields appear nowhere — exclusion by construction from the same `sensitivityFlag` declaration that drives activation.
- Given the export is fetched, when it completes, then `SCHEDULE_EXPORTED` is audited with included/excluded COUNTS — never content.
- Given the suite, when DoD line 4 is proven, then the proof is a test export fetched over HTTP whose body is asserted to contain the non-sensitive item and to NOT contain the sensitive item's text anywhere.
- Given the UI, when a schedule-bearing form renders, then an "Export non-sensitive schedule" action is available to the draft owner (no permission needed — the artefact contains nothing sensitive).

## Notes & Constraints
- CSV quoting per RFC 4180 — a description containing a comma or quote must not shift columns.
- PDF export is UC-09; this story deliberately ships the minimal provable artefact (Q7 records the
  format question).

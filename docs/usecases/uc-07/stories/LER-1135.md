# LER-1135 — Access logging — every MG6D view and edit

_UC-07 Sensitive Material Handling · epic: `docs/usecases/uc-07/epic.md` · PRD: `docs/usecases/uc-07/prd.md`_

_Client ticket **LER-1135** (Story, To Do) · delivering ticket: **LER-1249** · build order: story 10 of 15, stage 3._

## User Story
As a compliance-minded practice, we want every view and edit of the sensitive section on the record with who and when, so that later challenge meets evidence rather than memory.

## Acceptance Criteria
- Given a permitted user opens a draft whose section is active, when the GET returns the section content, then `SENSITIVE_SECTION_VIEWED` is recorded — user identity (`userId`) and timestamp (`createdAt`) on the row itself.
- Given a confirmed save touching sensitive fields, when it lands, then `SENSITIVE_SECTION_EDITED` is recorded with the touched field ids and the confirmation id — never field values.
- Given a rejected attempt (no permission, no/foreign confirmation), when the guard fires, then `SENSITIVE_ACCESS_DENIED` records the caller's identity and mode.
- Given confirmations and acknowledgements, when they are recorded, then `SENSITIVE_INSTRUCTIONS_CONFIRMED` / `SENSITIVE_PII_ACKNOWLEDGED` rows carry the wording hash.
- Given the suite, when DoD line 3 is proven, then the checks read the audit rows back from the database and assert the acting user's id and a sane timestamp on each — view AND edit distinguished by action name.

## Notes & Constraints
- All through the existing `AuditService.record()` — the append-only path; a failed audit write never
  breaks the user's action (existing contract).
- The dashboard LIST endpoint redacts but does not log views: a listing never contains section content,
  so it is not a view of MG6D (PRD §4.6 records the reasoning).
- Metadata carries ids, counts and hashes only — never case content.

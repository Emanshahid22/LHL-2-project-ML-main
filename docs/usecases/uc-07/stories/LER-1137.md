# LER-1137 — Step-up acknowledgement on every access

_UC-07 Sensitive Material Handling · epic: `docs/usecases/uc-07/epic.md` · PRD: `docs/usecases/uc-07/prd.md`_

_Client ticket **LER-1137** (Story, To Do) · delivering ticket: **LER-1251** · build order: story 12 of 15, stage 2._

## User Story
As a compliance-minded practice, we want the handling confirmation demanded on every access to the section, not once per login, so that familiarity never erodes the gate.

## Acceptance Criteria
- Given a user confirmed the instructions and edited the section, when they reload the page (or navigate away and back, or open a new tab), then the section is locked again and editing requires a fresh confirmation.
- Given each fresh confirmation, when it is recorded, then it is a NEW persisted row — the trail shows every access-grant, not the latest.
- Given the client session, when the confirmation id is held, then it lives in memory only (a session service), never in localStorage or a cookie — persistence anywhere would silently convert per-access into per-forever.
- Given the suite, when step-up is proven, then the check confirms, saves, reloads, observes the locked state, confirms again, and asserts two acknowledgement rows exist.

## Notes & Constraints
- Explicit scope requirement; the cadence question for the PII acknowledgement is separate and recorded
  (open-questions Q6).
- "Access" = a fresh rendering context for the section. The definition is recorded in the PRD (§4.8) so
  a future reviewer argues with the definition, not the implementation.

# LER-1139 — Locked message names the required permission level and its holders

_UC-07 Sensitive Material Handling · epic: `docs/usecases/uc-07/epic.md` · PRD: `docs/usecases/uc-07/prd.md`_

_Client ticket **LER-1139** (Story, To Do) · delivering ticket: **LER-1253** · build order: story 14 of 15, stage 1._

## User Story
As a defence solicitor locked out of a sensitive section, I want to be told exactly which permission I need and who in the firm has it, so that the lock is a door with a doorbell rather than a wall.

## Acceptance Criteria
- Given the locked state, when it renders, then the message names the required level — Sensitive Material Access, the shared `SENSITIVE_PERMISSION_LEVEL` constant, one source of truth for guard, DTO and copy.
- Given the firm's users, when the locked DTO block is computed, then `permissionHolders` lists the NAMES of users holding the permission (in the demo seed: Alex Marlowe), and the locked message shows them as who to ask.
- Given nobody holds the permission, when the locked state renders, then the message says so honestly rather than showing an empty list.
- Given the naming question, when the copy ships, then it does not present the level name as settled — open-questions Q2 records that naming and real-world assignment are practitioner calls.

## Notes & Constraints
- Names only — never emails or ids in the UI copy. Listing holders inside one firm is the requirement
  ("who in the firm has it"), not a leak; Q2 records the policy question all the same.
- There is deliberately NO UI to grant the permission (PRD §5): granting sensitive access is itself a
  sensitive act and ships only with a decision on who may perform it.

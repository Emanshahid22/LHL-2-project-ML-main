# LER-1130 — Confirmation not bypassable in the UI

_UC-07 Sensitive Material Handling · epic: `docs/usecases/uc-07/epic.md` · PRD: `docs/usecases/uc-07/prd.md`_

_Client ticket **LER-1130** (Story, To Do) · delivering ticket: **LER-1244** · build order: story 05 of 15, stage 2._

## User Story
As a compliance-minded practice, we want no interface path that reaches an editable MG6D section without the confirmation, so that the gate is a property of the product rather than of user goodwill.

## Acceptance Criteria
- Given any way of arriving at an active section (fresh load, navigation, activation mid-session, autofill, the wizard shell — anywhere `DynamicForm` renders), when the section is unconfirmed, then its fields have no form controls at all: nothing to type into, nothing for autosave to send.
- Given the E2E suite, when it probes for bypasses, then it proves: no input/select/textarea inside the section pre-confirmation; the page FormGroup lacks the sensitive field ids pre-confirmation; and a save fired pre-confirmation carries no sensitive keys.
- Given a mid-session activation (user marks a row sensitive while editing), when the section appears, then it appears in the unconfirmed state — activation never inherits an unlocked state from nowhere.

## Acceptance note
This story is delivered by construction (open-questions F2: sensitive fields are excluded from the base
FormGroup and added only on confirmation), and the checks assert the construction holds.

## Notes & Constraints
- First half of the requirement; LER-1131 is the half that actually holds against a hostile client.
- Do not deliver this with `disabled` attributes or CSS: a disabled control still exists and still
  carries a value; the section's controls must not exist pre-confirmation.

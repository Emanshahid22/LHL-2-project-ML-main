# LER-1129 — Confirmation before editing

_UC-07 Sensitive Material Handling · epic: `docs/usecases/uc-07/epic.md` · PRD: `docs/usecases/uc-07/prd.md`_

_Client ticket **LER-1129** (Story, To Do) · delivering ticket: **LER-1243** · build order: story 04 of 15, stage 2._

## User Story
As a defence solicitor, I want to explicitly confirm I have read and understood the handling instructions before the section will let me edit, so that handling sensitive material is an act I own, not a default I fell into.

## Acceptance Criteria
- Given a permitted user and an active, unconfirmed section, when it renders, then existing MG6D rows are read-only and a "I have read and understood the handling instructions" checkbox plus Confirm button are the only path forward.
- Given the checkbox unticked, when the user looks at Confirm, then it is disabled — the affirmative step is the tick plus the press, not a stray click.
- Given Confirm is pressed, when the API records it, then `POST /drafts/:id/sensitive/confirmations` writes a persisted per-user `SensitiveAcknowledgement` row (kind HANDLING_INSTRUCTIONS, with the wording hash) and an audit event, and returns the confirmation id the save path will carry.
- Given the confirmation succeeds, when the section unlocks, then the MG6D controls join the page form and autosave carries `sensitiveConfirmationId` on every save that touches them.
- Given a user WITHOUT the permission, when they attempt the confirmation endpoint directly, then 403, audited as denied — confirmation is not a way around the lock.

## Notes & Constraints
- Per-user, persisted, auditable — the scope's own words; rows are append-only like everything else here.
- The endpoint 409s when the section is not active: confirming instructions for a form with no sensitive
  material is a client bug, not a recordable act.

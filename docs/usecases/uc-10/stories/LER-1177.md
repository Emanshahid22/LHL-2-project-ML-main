# LER-1177 — New version on regeneration

_UC-10 Form Archive & Case Attachment · epic: `docs/usecases/uc-10/epic.md` · PRD: `docs/usecases/uc-10/prd.md`_

_Client ticket **LER-1177** (Story, To Do) · delivering ticket: to be created after pack review · build order: story 1 of 16, stage 1._

## User Story
As the archive engine, we want every successful generation whose content differs from the lineage's latest version to mint the next version number, so that V2, V3 and so on are assigned by the engine and never by a client.

## Acceptance Criteria
- Given a first successful generation on a lineage, when it stores, then `ArchivedVersion` V1 exists with label "Original", in the same transaction as the document row.
- Given an amendment draft's generation, when it stores, then the next monotonic version mints with label "Amendment N" (N = amendment cycle), unique per `(lineageId, versionNumber)`.
- Given a regeneration with byte-identical content, when it stores, then a NEW version row still mints, pointing at the same immutable stored file — version identity is row-level, not content-level (Phase-1 review, condition 1); content-addressing dedupes bytes, never history.

## Notes & Constraints
- Label rule and multi-version-per-cycle interpretation: PRD §11. Version numbers are engine-assigned (client ticket's own words) — no API accepts a number.
- `planVersionMint()` takes no content input by construction — byte-identity cannot suppress a mint (unit-pinned).
- `valuesSnapshotJson` and `containsSensitive` are captured at mint from the render model already in hand — never recomputed from stored bytes.

## Definition of Done
- Minting logic + unit tests (label derivation, idempotence); e2e proves V1→V2 on amendment and no-mint on identical regeneration.

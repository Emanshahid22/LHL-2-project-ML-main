## User Story
As a defence solicitor, I want certainty that completing a form cannot alter the case file, so that the case record stays the authoritative source rather than something my form edits.

## Acceptance Criteria
- Given any operation in the product, when it runs, then no code path writes to the `Case` or `CaseOffence` tables — the API exposes only `GET /api/cases` and `GET /api/cases/:id`.
  - COVERAGE GAP — no automated check asserts the absence of a write path. See `open-questions.md` G1.
- Given a populated draft, when the case is later read again, then the values live on the draft rather than having been written back to the case.
  - Covered by: e2e/uc02-autofill.spec.ts › `provenance records the source, the value and the case timestamp`
- Given a case-linked draft, when population runs, then the only rows written are the draft and its audit event.
  - Covered by: e2e/uc02-autofill.spec.ts › `auto-fill writes an AUTO_POPULATED audit event`

## Notes & Constraints

- The guarantee is **structural**: `CasesService` has no create, update or delete method, and
  `cases.controller.ts` declares only two `@Get` routes. That is stronger than a rule someone follows,
  but it is not currently asserted by a test — an accidental future write path would not fail the suite.
- Recorded as a coverage gap rather than claimed as covered.

- Resolver: `libs/shared/src/lib/autofill.ts` (pure). Service: `apps/api/src/drafts/drafts.service.ts`.
  Badges and notes: `apps/web/src/app/shared/dynamic-form/dynamic-form.ts`.
- **`mapsTo` only where the case datum genuinely IS the field.** An MG11 witness is not the defendant;
  MG16 `subjectName` stays unmapped pending a legal ruling. Never map signatures or non-OIC officers.
- Provenance matching is a `JSON.stringify` comparison, so dates must stay ISO strings in controls —
  `provideNativeDateAdapter` would silently kill every badge (CLAUDE.md rule 7).
- **Additive only:** a field id is permanent; `valuesJson` and `autoFillJson` are both keyed by id.

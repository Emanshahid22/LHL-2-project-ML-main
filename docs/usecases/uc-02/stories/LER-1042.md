## User Story
As a defence solicitor, I want the form to read the case it is linked to and nothing else, so that a form can only ever be populated from a file I am entitled to see.

## Acceptance Criteria
- Given a case-linked draft, when auto-fill runs, then it reads that draft's case and populates from it.
  - Covered by: e2e/uc02-autofill.spec.ts › `first open of a case-linked draft populates and summarises`
- Given a standalone draft, when auto-fill is requested, then it is refused with an explanation, and nothing is populated when the draft is opened.
  - Covered by: e2e/uc02-autofill.spec.ts › `a standalone draft is rejected for auto-fill and never populates on open`
- Given a case granted only to a colleague, when I request it, then it is not readable.
  - Covered by: e2e/uc01-form-selection.spec.ts › `a case belonging only to a colleague is not readable`
- Given another user's draft, when I request it, then it is not readable, so its case cannot be reached through it.
  - Covered by: e2e/uc01-form-selection.spec.ts › `another user's draft is not readable`

## Notes & Constraints

- Every case read goes through `CasesService.findForUser` (a `CaseAccess` join). There is no unscoped
  case query in the API.
- An inaccessible case id answers **404, not 403**: a 403 would confirm the case exists, which is itself
  a disclosure.

- Resolver: `libs/shared/src/lib/autofill.ts` (pure). Service: `apps/api/src/drafts/drafts.service.ts`.
  Badges and notes: `apps/web/src/app/shared/dynamic-form/dynamic-form.ts`.
- **`mapsTo` only where the case datum genuinely IS the field.** An MG11 witness is not the defendant;
  MG16 `subjectName` stays unmapped pending a legal ruling. Never map signatures or non-OIC officers.
- Provenance matching is a `JSON.stringify` comparison, so dates must stay ISO strings in controls —
  `provideNativeDateAdapter` would silently kill every badge (CLAUDE.md rule 7).
- **Additive only:** a field id is permanent; `valuesJson` and `autoFillJson` are both keyed by id.

# LER-1086 — Renumbering confirmation dialog

_UC-04 MG6 Unused Material Schedule · epic: `docs/usecases/uc-04/epic.md` · PRD: `docs/usecases/uc-04/prd.md`_

## User Story
As a defence solicitor, I want to be asked before a deletion renumbers the schedule, so that I never silently change the references other documents cite.

## Acceptance Criteria
- Given a schedule with rows, when I press delete on a row, then a confirmation dialog appears before anything is removed, carrying `data-testid="renumber-confirm"`.
- Given the dialog is open, when I read it, then it names the item being removed and states that the items below it will be renumbered.
- Given the dialog is open, when I cancel, then nothing changes — the row remains, the ordinals are unchanged, and no save is triggered. Cancel is a true no-op.
- Given the dialog is open, when I confirm, then the row is removed and the remaining items renumber.
- Given the scope's Definition of Done requires "Renumbering on deletion prompts user confirmation before executing", when the flow is tested, then a check proves the prompt precedes the mutation, not follows it.

## Notes & Constraints

- Files: `libs/shared/src/lib/form-template.types.ts` and `form-templates.ts`; renderer in
  `apps/web/src/app/shared/dynamic-form/`; pure logic in `libs/shared/src/lib/schedule.ts`.
- **Designation independence:** no behaviour may branch on the form code — the MG6 designation is
  disputed (`docs/answers/LER-1205-designation-mismatches.md`) and this build must not wait for it.
- **Additive only:** never rename or delete an existing field id; run `npm run orphan-scan` around any
  id change.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib
  rebuilds and will serve stale templates.
- Full mechanism and business rules: `docs/usecases/uc-04/prd.md` (§4 and §8).

# LER-1087 — Renumber on delete

_UC-04 MG6 Unused Material Schedule · epic: `docs/usecases/uc-04/epic.md` · PRD: `docs/usecases/uc-04/prd.md`_

## User Story
As a defence solicitor, I want removing an item to renumber the rest immediately and correctly, so that the schedule stays accurate as I work.

## Acceptance Criteria
- Given a 3-item schedule, when I delete item 2 and confirm, then the survivors display as 1 and 2, in their original relative order.
- Given items are renumbered after a delete, when their identities are inspected, then every surviving `__id` is unchanged — disclosure history survives renumbering intact.
- Given the last remaining row is deleted, when the schedule re-renders, then it is empty and a required schedule reads incomplete.
- Given a delete is confirmed, when autosave fires, then the persisted array matches what is displayed, with no ordinal stored.

## Notes & Constraints

- Files: `libs/shared/src/lib/form-template.types.ts` and `form-templates.ts`; renderer in
  `apps/web/src/app/shared/dynamic-form/`; pure logic in `libs/shared/src/lib/schedule.ts`.
- **Designation independence:** no behaviour may branch on the form code — the MG6 designation is
  disputed (`docs/answers/LER-1205-designation-mismatches.md`) and this build must not wait for it.
- **Additive only:** never rename or delete an existing field id; run `npm run orphan-scan` around any
  id change.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib
  rebuilds and will serve stale templates.
- Full mechanism and business rules: `docs/usecases/uc-04/prd.md` (§4 and §8).

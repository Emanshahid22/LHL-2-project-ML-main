# LER-1084 — Computed ordinal numbering

_UC-04 MG6 Unused Material Schedule · epic: `docs/usecases/uc-04/epic.md` · PRD: `docs/usecases/uc-04/prd.md`_

## User Story
As a defence solicitor, I want each item's displayed number to be derived from its position, so that the numbering can never disagree with the schedule.

## Acceptance Criteria
- Given a schedule of n rows, when it renders, then the displayed numbers are 1..n in order.
- Given the ordinal is displayed, when the draft is saved, then **no ordinal is stored anywhere** in `valuesJson` — a stored counter is a defect.
- Given a row is inserted or removed, when the schedule re-renders, then ordinals recompute automatically with no explicit renumber step in the code.
- Given the pure helper `withOrdinals(rows)` in `libs/shared`, when it is called, then it returns rows annotated with `index + 1` and is unit-tested independently of the UI.

## Notes & Constraints
- Renumbering is therefore not an operation — it is what happens when the array changes. Keep it that way.

- Files: `libs/shared/src/lib/form-template.types.ts` and `form-templates.ts`; renderer in
  `apps/web/src/app/shared/dynamic-form/`; pure logic in `libs/shared/src/lib/schedule.ts`.
- **Designation independence:** no behaviour may branch on the form code — the MG6 designation is
  disputed (`docs/answers/LER-1205-designation-mismatches.md`) and this build must not wait for it.
- **Additive only:** never rename or delete an existing field id; run `npm run orphan-scan` around any
  id change.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib
  rebuilds and will serve stale templates.
- Full mechanism and business rules: `docs/usecases/uc-04/prd.md` (§4 and §8).

## Definition of Done

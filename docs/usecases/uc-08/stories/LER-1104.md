# LER-1104 — Cross-form rules — the declared shared vocabulary

_UC-08 Form Review & Quality Check · epic: `docs/usecases/uc-08/epic.md` · PRD: `docs/usecases/uc-08/prd.md`_

_Client ticket **LER-1104** (Story, To Do) · delivering ticket: **LER-1259** · build order: story 05 of 14, stage 1._

## User Story
As the product, we want cross-form rules to run only on a vocabulary the templates explicitly declare, so that "the forms share one vocabulary" is a checked fact rather than an assumption.

## Acceptance Criteria
- Given the shared types, when this story ships, then `FormFieldDefinition` carries an optional `crossRef: { vocabulary: 'exhibitReference'; role: 'defines' | 'cites' }` — DECLARED, never inferred, the `narrative`/`sensitive` discipline applied to cross-form identity.
- Given the templates, when this story ships, then MG12 `exhibitEntries` declares `defines` and MG11 `exhibitsReferenced` declares `cites` — the two fields whose helpText already documents the same reference convention — and nothing else is annotated.
- Given conformance, when it runs, then invalid vocabularies/roles, `crossRef` on non-text fields, and a template citing a vocabulary nothing defines are build failures, with planted-defect self-tests in both directions.
- Given LER-1104's own example ("a witness named in MG5 must have a corresponding MG11"), when this story ships, then it is recorded as NOT structurally possible today (MG5 has no witness field; open-questions F1/Q4) — the engine and vocabulary ship, the witness rule waits for evidence, and no field is invented to fake it.

## Notes & Constraints
- Template edits are ADDITIVE (annotation only, no new fields, no id changes); templateVersion
  bumps on MG11 and MG12; `orphan-scan` must stay clean.
- The vocabulary type is a union of one on purpose: a second vocabulary must argue its way in with
  the same documentation bar, not arrive as a string.

# LER-1149 — Advisory acknowledgement

_UC-08 Form Review & Quality Check · epic: `docs/usecases/uc-08/epic.md` · PRD: `docs/usecases/uc-08/prd.md`_

_Client ticket **LER-1149** (Story, To Do) · delivering ticket: **LER-1264** · build order: story 10 of 14, stage 3._

## User Story
As a defence solicitor, I want to acknowledge an advisory finding and proceed, so that a heuristic's caution does not hold my form hostage — while my decision to proceed is on the record.

## Acceptance Criteria
- Given an advisory issue, when its checklist row renders, then it offers an acknowledgement control (LER-1106 adds the required reason).
- Given unacknowledged advisories, when the user looks at Finalise, then it stays disabled; acknowledging every advisory (with blocking at zero) enables it.
- Given a finalise request, when it carries the acknowledgements, then each is validated server-side against the CURRENT engine run — an acknowledgement for a finding that no longer exists is ignored, and a current advisory without one rejects the request (409).
- Given a fresh review run, when the panel re-renders, then previous acknowledgements are reset — a reason given for last week's finding does not silently cover today's (open-questions Q7).

## Notes & Constraints
- Acknowledgements are audited at the finalise boundary (`ADVISORY_BYPASSED`, one row per finding)
  rather than persisted as state — the record is the point, not a sticky bypass.
- Finding identity is the stable `issueId` (open-questions D3), so acknowledgement targets exactly
  one finding.

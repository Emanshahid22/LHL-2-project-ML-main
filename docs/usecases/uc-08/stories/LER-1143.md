## User Story
As a defence solicitor, I want impossible dates and out-of-order dates caught at review, so that a chronology error is fixed before a prosecutor finds it.

## Acceptance Criteria
- Given a date field holding a value that is neither empty nor a real ISO date (including the IsoDateAdapter's `'invalid'` sentinel), when the suite runs, then Check 2 reports it blocking.
- Given the template's DECLARED `notBefore`/`notAfter` rules, when the suite runs, then each violated rule becomes an issue carrying the rule's own severity — declared `error` blocks, declared `advisory` advises.
- Given a comparison that could not run (UC-05's suppressed findings — e.g. ambiguous case data), when the suite runs, then it surfaces as an advisory "could not compare" note, never as silence and never as a failure.
- Given all dates valid and ordered, when the suite runs, then Check 2 is clean.

## Notes & Constraints
- REUSES `crossFieldFindings` — the UC-05 rule set, as LER-1143's client description says. No new
  ordering rule is invented here, and **target dates keep no `noFutureDate`** (the UC-04 lesson:
  an MG6 target date legitimately lies in the future).
- Severity mapping is the engine's table (open-questions Q3), one line per finding kind.

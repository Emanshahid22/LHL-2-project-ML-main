# LER-1150 — Finalise gating — enforced at the API, not just the button

_UC-08 Form Review & Quality Check · epic: `docs/usecases/uc-08/epic.md` · PRD: `docs/usecases/uc-08/prd.md`_

_Client ticket **LER-1150** (Story, To Do) · delivering ticket: **LER-1266** · build order: story 12 of 14, stage 2._

## User Story
As a compliance-minded practice, we want finalisation refused at the endpoint whenever the gate's conditions are unmet, so that the gate holds against any client, not just our own UI.

## Acceptance Criteria
- Given outstanding blocking issues, when `POST /drafts/:id/finalise` is called directly, then 409, nothing changes, and `FINALISE_REJECTED` is audited with why (counts, not content).
- Given an active-but-unconfirmed MG6D section, when finalise is called, then the same refusal — UC-07's confirmation reaches the end of the form's life (Check 4 at the boundary).
- Given an incomplete check (timeout/failure), when finalise is called, then refused — a timeout is not a bypass (open-questions Q5).
- Given a clean run with every advisory acknowledged-with-reason, when finalise is called, then the draft becomes FINALISED, `FORM_FINALISED` is audited, and subsequent edits are refused by the existing status guard while the UI renders the form read-only with the UC-09 stub.
- Given the gate, when it evaluates, then it RE-RUNS the engine at the boundary — it never trusts a report the client did earlier.

## Notes & Constraints
- Same discipline as UC-07's confirmation gate: the endpoint is the boundary; every refusal is on
  the record; 409 for state conflicts (the draft is not in a finalisable state), 422 for shape.
- `REVIEWED` is evidence, not authority (open-questions Q1): finalise from DRAFT or REVIEWED is
  equally re-checked.

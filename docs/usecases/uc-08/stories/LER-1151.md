# LER-1151 — Quality check outcome logged — evidence it ran

_Client ticket **LER-1151** (Story, To Do) · delivering ticket: **LER-1267** · build order: story 13 of 14, stage 2._

## User Story
As a compliance-minded practice, we want every quality-check run in the audit trail whatever its outcome, so that we can prove the check ran, not merely that nothing failed.

## Acceptance Criteria
- Given any review run — clean, issue-laden, or partially incomplete — when it completes, then `QUALITY_CHECK_COMPLETED` is recorded with the per-check outcomes and the blocking/advisory/incomplete counts, and never a field value.
- Given a refused finalisation, when it is rejected, then `FINALISE_REJECTED` records the refusal and its reason class; given a successful one, `FORM_FINALISED` records it.
- Given a reviewed draft that is then edited, when the save lands, then the save's audit metadata notes the review was invalidated (`reviewInvalidated: true`) — the trail explains why a REVIEWED form is DRAFT again (open-questions F3).
- Given the audit table, when these rows are written, then it is through the existing append-only `AuditService.record()` — no new write path, no update, no delete.

## Notes & Constraints
- The COMPLETENESS_CHECKED precedent (UC-04) set the principle: a check that only logs failures
  cannot prove it ran. Same here, at review scale.

# LER-1148 — Blocking issues must resolve

_UC-08 Form Review & Quality Check · epic: `docs/usecases/uc-08/epic.md` · PRD: `docs/usecases/uc-08/prd.md`_

_Client ticket **LER-1148** (Story, To Do) · delivering ticket: **LER-1263** · build order: story 09 of 14, stage 3._

## User Story
As a compliance-minded practice, we want blocking findings to be unresolvable by anything except fixing the form, so that the gate cannot be talked out of its job.

## Acceptance Criteria
- Given a blocking issue, when its checklist row renders, then it carries NO acknowledgement control of any kind — the distinction from advisory handling is structural, not a disabled button.
- Given outstanding blocking issues, when the user looks at Finalise, then it is disabled; and given a direct `POST /drafts/:id/finalise` while they stand, then 409 with `FINALISE_REJECTED` audited (LER-1150's server half proves this).
- Given a blocking issue is fixed in the form, when review runs again, then the issue is gone because the form changed — the only exit a blocking issue has.

## Notes & Constraints
- First half of the scope's step 7; LER-1149/1106 are the advisory half. The two halves must be
  visibly different in the UI and behaviourally different at the API.

# LER-1106 — Advisory override with reason — written to the audit log

_UC-08 Form Review & Quality Check · epic: `docs/usecases/uc-08/epic.md` · PRD: `docs/usecases/uc-08/prd.md`_

_Client ticket **LER-1106** (Story, To Do) · delivering ticket: **LER-1265** · build order: story 11 of 14, stage 2._

## User Story
As a compliance-minded practice, we want every bypassed advisory to carry the solicitor's own reason in the audit trail, so that later review meets a decision with its justification attached.

## Acceptance Criteria
- Given an advisory acknowledgement control, when the user acknowledges, then a free-text reason is REQUIRED — empty or whitespace does not count, in the UI or at the API.
- Given a finalise request with acknowledgements, when it succeeds, then one `ADVISORY_BYPASSED` audit row exists per bypassed finding, carrying `{ issueId, checkId, fieldId, reason }` with the reason recorded verbatim.
- Given a finalise request whose acknowledgement lacks a reason, when the API validates it, then 409 — a reasonless override is not an override, it is a click.
- Given the audit trail, when a bypassed advisory is read back, then the row identifies the user (userId) and moment (createdAt) exactly as every other audit row does.

## Notes & Constraints
- This is the client's original UC-05-era ticket, reserved for UC-08 — its description ("Advisory
  issues may be overridden; the reason is recorded — written to the audit log") is honoured
  literally: the reason string goes into the audit metadata, and nothing else about the draft
  changes.
- The reason is the user's own words about their own decision — recording it verbatim is the
  point; truncation or paraphrase would falsify the record. (Length cap 500 chars, matching the
  UC-06 suggestion-audit cap.)

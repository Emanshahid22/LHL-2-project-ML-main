# LER-1217 — Offence date after charge date is flagged

_UC-05 Field Validation · epic: `docs/usecases/uc-05/epic.md` · PRD: `docs/usecases/uc-05/prd.md`_

_DevOps Bot ticket **LER-1217** (Story, To Do) · build stage order: story 11 of 16._

## User Story
As a defence solicitor, I want a charge dated before its offence flagged as an error, so that an impossible chronology never reaches the court file.

## Acceptance Criteria
- Given an MG4 draft linked to a case with exactly one offence date, when `chargeDate` is earlier than that offence date, then an **error**-severity finding appears in the Consistency Issues panel.
- Given the same draft, when `chargeDate` is later than the offence date, then no finding appears.
- Given the same draft, when `chargeDate` equals the offence date, then no finding appears — same-day charge is normal.
- Given a case with two different offence dates, when the check runs, then it is suppressed and the panel explains that the case holds conflicting offence dates so the check could not run.
- Given a standalone MG4 draft, when the check runs, then it is suppressed silently — there is no case file to compare against.
- Given a flagged finding, when I correct `chargeDate`, then the finding clears automatically.
- Given the scope's Definition of Done line "Cross-field check: offence date after charge date is flagged correctly in all tested cases", when the suite runs, then all five cases above are covered.

## Notes & Constraints

- **Why it is a case-vs-form rule:** no template carries both dates. MG4 has `chargeDate` and no offence
  date; MG3 and MG5 have `offenceDate` and no charge date. Adding an offence-date box to MG4 was rejected —
  MG4 was rebuilt from a genuine specimen with every field corroborated, and inventing a box to satisfy a
  validation rule is the failure CLAUDE.md rule 1 forbids.
- The case datum comes from `resolveCaseField('offenceDate', case)`, which already returns `ambiguous` when
  a case has several offences. That is what makes the suppression case testable with the seeded
  two-offence case (Marcus Bellamy).
- This is the DoD line most likely to be read as "just add a validator". It is not: the whole point is where
  the second operand comes from.

- Rule engine: `libs/shared/src/lib/validation.ts` (new, pure). Types:
  `libs/shared/src/lib/form-template.types.ts`. Rules on fields: `form-templates.ts`.
- **No invented format.** A format may be `error` severity only if its provenance is `documented` with a
  cited source. Everything else is advisory. This is enforced by `severityFor()` and by
  `npm run conformance` — not by good intentions.
- **Additive only:** never rename or delete a field id; bump `templateVersion` on any template whose rules
  change; run `npm run orphan-scan` around any id change.
- Reuse the shared renderer. Do not special-case a form code; a rule is declared on the field that owns it.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib rebuilds.
- Full mechanism and business rules: `docs/usecases/uc-05/prd.md` (§4 and §8).

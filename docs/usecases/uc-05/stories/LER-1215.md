# LER-1215 — Cross-field rule engine

_UC-05 Field Validation · epic: `docs/usecases/uc-05/epic.md` · PRD: `docs/usecases/uc-05/prd.md`_

_DevOps Bot ticket **LER-1215** (Story, To Do) · build stage order: story 09 of 16._

## User Story
As a defence solicitor, I want two values checked against each other, so that a file whose dates contradict themselves is caught before anyone relies on it.

## Acceptance Criteria
- Given a date field, when it declares `notAfter: { fieldId }` or `notBefore: { fieldId }`, then it is compared against that sibling field on the same template.
- Given a date field, when it declares `notAfter: { casePath }` or `notBefore: { casePath }`, then it is compared against a case datum resolved through UC-02's `resolveCaseField`.
- Given a cross-field rule, when only one of the two operands has a value, then **no finding is produced** — the scope's "cross-field checks run when a second dependent field is completed".
- Given a rule whose case datum resolves `ambiguous` (a case with two offence dates), when the check runs, then it is **suppressed** and the panel explains that the check could not run and why.
- Given a rule whose case datum resolves `no_data`, or a standalone draft with no case at all, when the check runs, then it is suppressed silently — there is nothing to compare against and nothing to explain.
- Given a rule pointing at a field id that does not exist, a non-date field, or an invalid `CaseFieldPath`, when `npm run conformance` runs, then it fails.
- Given each rule, when it is declared, then it carries its own severity and message, because some pairs are impossible and others merely unusual.

## Notes & Constraints

- Rules are declared **on the field that owns them**, so nothing keys off a form code — the same discipline
  UC-04 used for the schedule. A rule travels with its template.
- Suppression on `ambiguous` is the UC-02 discipline restated: report, never guess. Picking one of two
  offence dates to compare against would produce a confident wrong answer, which is worse than silence.
- The conformance rules matter more than usual here: a dangling field reference in a cross-field rule fails
  silently at runtime (nothing to compare, no finding), so only a build-time check catches it.

- Rule engine: `libs/shared/src/lib/validation.ts` (new, pure). Types:
  `libs/shared/src/lib/form-template.types.ts`. Rules on fields: `form-templates.ts`.
- **No invented format.** A format may be `error` severity only if its provenance is `documented` with a
  cited source. Everything else is advisory. This is enforced by `severityFor()` and by
  `npm run conformance` — not by good intentions.
- **Additive only:** never rename or delete a field id; bump `templateVersion` on any template whose rules
  change; run `npm run orphan-scan` around any id change.
- Reuse the shared renderer. Do not special-case a form code; a rule is declared on the field that owns it.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib rebuilds.
- Full mechanism and business rules: `docs/usecases/uc-05/prd.md` (§4 and §8).

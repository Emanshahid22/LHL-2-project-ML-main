# LER-1211 — Date format hint and impossible dates

_UC-05 Field Validation · epic: `docs/usecases/uc-05/epic.md` · PRD: `docs/usecases/uc-05/prd.md`_

_DevOps Bot ticket **LER-1211** (Story, To Do) · build stage order: story 05 of 16._

## User Story
As a defence solicitor, I want a date box to tell me the format it wants and refuse a date that cannot exist, so that 31/02 never silently becomes 3 March on a court document.

## Acceptance Criteria
- Given an empty or unparseable date field, when it has focus, then a format hint shows the expected DD/MM/YYYY shape.
- Given a date field, when I type an impossible date such as 31/02/2026, then it is rejected with "Enter a real date as DD/MM/YYYY" and is **not** rolled forward to 3 March.
- Given a date field, when I type a value that is not DD/MM/YYYY at all, then the same format message appears rather than a "required" message.
- Given a valid date, when it is stored, then storage is ISO `YYYY-MM-DD` while display stays DD/MM/YYYY.
- Given the scope's Definition of Done line "Date validation rejects DD/MM/YYYY format violations and impossible dates", when the suite runs, then a check proves both halves.

## Notes & Constraints

- Rejection and non-rollover are already delivered and asserted (`an impossible date is rejected at input`).
  **The delta is the hint**, which the scope asks for explicitly ("invalid format shows format hint").
- Order matters in the message function: `matDatepickerParse` is checked before `required`, because Material
  reports an unparseable date as an empty value and the required message would otherwise mask the cause.
- Do NOT switch to `provideNativeDateAdapter` — `Date` objects in controls break UC-02's provenance
  matching and would remove every auto-fill badge (CLAUDE.md rule 7).

- Rule engine: `libs/shared/src/lib/validation.ts` (new, pure). Types:
  `libs/shared/src/lib/form-template.types.ts`. Rules on fields: `form-templates.ts`.
- **No invented format.** A format may be `error` severity only if its provenance is `documented` with a
  cited source. Everything else is advisory. This is enforced by `severityFor()` and by
  `npm run conformance` — not by good intentions.
- **Additive only:** never rename or delete a field id; bump `templateVersion` on any template whose rules
  change; run `npm run orphan-scan` around any id change.
- Reuse the shared renderer. Do not special-case a form code; a rule is declared on the field that owns it.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib rebuilds.
- Full mechanism and business rules: `docs/usecases/uc-05/prd.md` (§4 and §8).

# LER-1221 — Server-side parity and the type-shape guard

_UC-05 Field Validation · epic: `docs/usecases/uc-05/epic.md` · PRD: `docs/usecases/uc-05/prd.md`_

_DevOps Bot ticket **LER-1221** (Story, To Do) · build stage order: story 15 of 16._

## User Story
As a defence solicitor, I want the server to hold the same view of validity as my browser, so that what the product tells me is not merely a courtesy the client could skip.

## Acceptance Criteria
- Given the rule engine, when it runs, then the same pure `validateForm(template, values, case?)` produces the findings the browser displays and the findings the API records — one implementation, not two.
- Given a saved MG11 draft with outstanding findings, when it is saved, then `DRAFT_SAVED` audit metadata carries `validationErrorCount` and `validationAdvisoryCount`.
- Given the audit metadata, when it is inspected, then it holds **counts only** — never a field value and never a failing string.
- Given a client sending a non-boolean into a `checkbox` field, a non-ISO string into a `date` field, a non-finite `number`, or an object where a scalar belongs, when the save is attempted, then the API returns **422** with the field named.
- Given a client sending a badly formatted URN, a missing required field, or a contradictory pair of dates, when the save is attempted, then it **saves** — a draft is allowed to be incomplete and inconsistent.
- Given the suite, when it runs, then a check proves the browser and a direct API call agree on the findings for the same values.

## Notes & Constraints

- **The split is deliberate and worth stating in the PR:** the API rejects what it cannot safely *store*
  (type shape) and records what is merely *wrong* (semantics). Rejecting a draft for a semantic rule would
  break autosave — a form is invalid for most of the time a human is filling it in.
- This closes the gap the README has admitted since UC-01: the declarative rules "are already framework-free;
  re-run them in the API".
- The finalisation gate — refusing to finalise while errors remain — is what `validateForm` exists for, and
  is **unreachable** until a finalise action exists (UC-10). Write the hook, document it, do not invent an
  endpoint for it.
- The type-shape guard runs before anything is written, alongside the existing declaration and group guards.

- Rule engine: `libs/shared/src/lib/validation.ts` (new, pure). Types:
  `libs/shared/src/lib/form-template.types.ts`. Rules on fields: `form-templates.ts`.
- **No invented format.** A format may be `error` severity only if its provenance is `documented` with a
  cited source. Everything else is advisory. This is enforced by `severityFor()` and by
  `npm run conformance` — not by good intentions.
- **Additive only:** never rename or delete a field id; bump `templateVersion` on any template whose rules
  change; run `npm run orphan-scan` around any id change.
- Reuse the shared renderer. Do not special-case a form code; a rule is declared on the field that owns it.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib rebuilds.
- Full mechanism and business rules: `docs/usecases/uc-05/prd.md` (§4 and §8).

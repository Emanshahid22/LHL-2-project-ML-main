# LER-1216 — Consistency Issues panel

_DevOps Bot ticket **LER-1216** (Story, To Do) · build stage order: story 10 of 16._

## User Story
As a defence solicitor, I want problems that span two fields listed together, so that I can see how the file contradicts itself rather than hunting for a message under one box.

## Acceptance Criteria
- Given one or more cross-field findings, when the form renders, then they appear in a **Consistency Issues** panel below the form section, carrying `data-testid="consistency-issues"`.
- Given a cross-field finding, when it is displayed, then it names both fields involved and states the relationship that failed.
- Given a cross-field finding, when the inline error slots are inspected, then **none of them holds it** — the scope requires cross-field errors "not inline".
- Given no cross-field findings, when the form renders, then the panel is absent rather than present and empty.
- Given a mixture of error and advisory findings, when the panel renders, then errors are distinguishable from advisories, with advisories in the design system's amber and errors in its error token.
- Given an `unverified` template, when the panel renders, then it states that a clean panel is not practitioner sign-off, so an absence of findings cannot be read as approval.
- Given a suppressed check, when the panel renders, then it carries a line saying the check could not run and why.

## Notes & Constraints

- Amber for advisory; the error token for errors. **Red stays reserved for UC-07 sensitive material**
  (CLAUDE.md rule 6) — the panel must not introduce a third red.
- `role="status"` so findings are announced without stealing focus; the panel is a labelled landmark.
- The last two criteria are the honesty ones. A validation panel is exactly where a user would over-read a
  clean result, and most templates are not verified.

- Rule engine: `libs/shared/src/lib/validation.ts` (new, pure). Types:
  `libs/shared/src/lib/form-template.types.ts`. Rules on fields: `form-templates.ts`.
- **No invented format.** A format may be `error` severity only if its provenance is `documented` with a
  cited source. Everything else is advisory. This is enforced by `severityFor()` and by
  `npm run conformance` — not by good intentions.
- **Additive only:** never rename or delete a field id; bump `templateVersion` on any template whose rules
  change; run `npm run orphan-scan` around any id change.
- Reuse the shared renderer. Do not special-case a form code; a rule is declared on the field that owns it.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib rebuilds.
- Full mechanism and business rules: `docs/usecases/uc-05/prd.md` (§4 and §8).

# LER-1213 — Officer collar number — 'Unverified format'

_UC-05 Field Validation · epic: `docs/usecases/uc-05/epic.md` · PRD: `docs/usecases/uc-05/prd.md`_

_DevOps Bot ticket **LER-1213** (Story, To Do) · build stage order: story 07 of 16._

## User Story
As a defence solicitor, I want an officer identifier checked only as far as we can actually check it, so that a correctly completed officer box is never marked wrong.

## Acceptance Criteria
- Given the registry, when `collarNumber` is defined, then it carries `provenance: 'inference'`, so it can only ever be advisory.
- Given the officer boxes as they exist today — MG1/MG3/MG4 `officerInCase`, MG5/MG16 `officerCompleting` — when the rules ship, then **none of them carries the `collarNumber` format**, because each box holds a name, a rank *and* a number in one free-text field and a pattern over it would reject correct input.
- Given a future dedicated collar-number field, when it declares the format, then a non-matching value shows the scope's wording — "Unverified format" — and does not block.
- Given the suite, when it runs, then a check asserts that no composite officer field carries a format rule, so a later well-meaning addition fails rather than quietly rejecting valid data.

## Notes & Constraints

- The scope asks for the collar number to be "validated against force-specific prefix where known; flagged as
  'Unverified format' if force unknown". There is **no force registry** in this product and no field holding
  a bare collar number, so "force unknown" is the universal case today. Shipping the advisory path only is
  the honest reading of the scope, not a shortfall against it.
- Adding a dedicated collar-number box to satisfy a validation rule would invert CLAUDE.md rule 1: a field
  needs evidence that the box exists on the real form first.
- The assertion in the last criterion is the important one — it protects the decision from being undone by
  someone who reads the scope and not this story.

- Rule engine: `libs/shared/src/lib/validation.ts` (new, pure). Types:
  `libs/shared/src/lib/form-template.types.ts`. Rules on fields: `form-templates.ts`.
- **No invented format.** A format may be `error` severity only if its provenance is `documented` with a
  cited source. Everything else is advisory. This is enforced by `severityFor()` and by
  `npm run conformance` — not by good intentions.
- **Additive only:** never rename or delete a field id; bump `templateVersion` on any template whose rules
  change; run `npm run orphan-scan` around any id change.
- Reuse the shared renderer. Do not special-case a form code; a rule is declared on the field that owns it.
- After changing `libs/shared`, **restart the API** — the nest watcher does not pick up shared-lib rebuilds.
- Full mechanism and business rules: `docs/usecases/uc-05/prd.md` (§4 and §8).

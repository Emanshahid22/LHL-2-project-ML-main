# LER-1071 — Page count from the renderer, never estimated

_UC-09 PDF Generation & Formatting · epic: `docs/usecases/uc-09/epic.md` · PRD: `docs/usecases/uc-09/prd.md`_

_Client ticket **LER-1071** (Story, To Do — deferred from UC-03) · delivering ticket: **LER-2394** · build order: story 04 of 26, stage 1/2._

## User Story
As the MG11 declaration's mechanism, we want the true page count taken from the paginated render itself, so that "consisting of N page(s)" can only ever state what was actually generated.

## Acceptance Criteria
- Given a rendered document, when generation completes, then the page count comes from the render result (Chromium's paginated output), is stored on the `GeneratedDocument` row, and no code path estimates it from content length.
- Given a one-page and a many-page MG11 (long narrative), when each renders, then the counts are 1 and N respectively and the count is exposed to the interpolation step (LER-1072) and the assertion (LER-1073).
- Given unit tests, when they run, then the count-extraction function is covered including the empty-document edge.

## Notes & Constraints
- Deferred from UC-03 precisely because estimation was the only option before a renderer existed; estimating now would re-import the defect the deferral avoided.

## Definition of Done
- Delivered against the criteria; unit + e2e coverage; full gate set green

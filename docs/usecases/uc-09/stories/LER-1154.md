# LER-1154 — Render pipeline: HTML/CSS Paged Media through Chromium

_UC-09 PDF Generation & Formatting · epic: `docs/usecases/uc-09/epic.md` · PRD: `docs/usecases/uc-09/prd.md`_

_Client ticket **LER-1154** (Story, To Do — names WeasyPrint/Jinja2) · delivering ticket: **LER-2374** · build order: story 06 of 26, stage 2 · **re-scoped, deviation D1**._

## User Story
As the API, we want a render pipeline that turns template + layout + draft values into a paginated PDF through the Chromium already pinned by the toolchain, so that layout is authored as HTML/CSS Paged Media (as the client ticket intended) without adding a Python runtime to a TypeScript monorepo.

## Acceptance Criteria
- Given a render job, when it runs, then a fresh Chromium renders the bound HTML with `@page` geometry, running header/footer and page-break rules, produces the PDF off the request path, and the browser is closed afterwards — no long-lived instance.
- Given a render exceeding the 30 s budget, when the timeout fires, then the job fails cleanly (LER-1168/1169 take over) and no partial file is stored.
- Given the deploy image, when the API boots, then a render self-test proves Chromium is present and working — a missing browser is a boot-time signal, not a first-click surprise.
- Given form content, when rendering, then nothing leaves the process: no external service, no network fetch in the rendered page (self-contained HTML, embedded styles).

## Notes & Constraints
- D1: the client original names WeasyPrint + Jinja2; the authoring model (HTML/CSS Paged Media) is kept, the engine is the one already in the toolchain. Playwright (or playwright-core + chromium) moves to a runtime dependency of the API — image-size impact measured in rollout (PRD §13).
- One render worker to start; SQLite is the bottleneck anyway. Measured in LER-1191.

## Definition of Done
- Delivered against the criteria; e2e renders at least MG11 and MG6 end to end
- Boot self-test observable in logs and covered by a check; full gate set green

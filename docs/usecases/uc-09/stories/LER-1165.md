# LER-1165 — Application-level AES-256 encryption at rest

_UC-09 PDF Generation & Formatting · epic: `docs/usecases/uc-09/epic.md` · PRD: `docs/usecases/uc-09/prd.md`_

_Client ticket **LER-1165** (Story, To Do) · delivering ticket: **LER-2385** · build order: story 10 of 26, stage 2 · **deviation D7** (limits stated)._

## User Story
As the custodian of criminal-case documents, we want every generated file encrypted at rest with AES-256 under application control, so that Global DoD #12 is a property this repo can verify rather than a platform attestation it can only cite (the LER-1202 lesson).

## Acceptance Criteria
- Given a generated document, when stored, then the bytes on disk are AES-256-GCM ciphertext (random 96-bit IV per file, auth tag stored) and a raw read of the file finds no `%PDF` magic and no plaintext form content.
- Given the two streaming endpoints (preview, download), when called by an authorised user, then decryption happens there and only there, streamed, never buffering whole files.
- Given a missing or malformed `DOCUMENT_MASTER_KEY`, when the API boots, then it refuses to start — the wording-integrity discipline; silent plaintext storage is impossible.
- Given a tampered stored file, when decryption runs, then GCM authentication fails and the endpoint answers honestly (410 + audit) rather than serving altered content.
- Given the `GeneratedDocument` row, when written, then it records cipher, IV and content hash — the "storage metadata" the DoD's verification names, checkable by LER-1192's storage audit.

## Notes & Constraints
- D7 limits, stated not hidden: one env-supplied master key, rotation = re-encrypt (a small tool ships with this story), no KMS/HSM on Railway. Q5 records the release-block question.
- Never log key material; never write plaintext temp files (render → encrypt in-process).

## Definition of Done
- Delivered against the criteria; e2e includes the raw-bytes-are-ciphertext check and the tamper case
- Unit: encrypt/decrypt round-trip + tamper-fails; full gate set green

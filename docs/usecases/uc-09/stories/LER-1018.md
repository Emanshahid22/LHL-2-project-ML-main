# LER-1018 — Storage-key PII scan: DoD #11 evidenced, continuously

_UC-09 PDF Generation & Formatting · epic: `docs/usecases/uc-09/epic.md` · PRD: `docs/usecases/uc-09/prd.md`_

_Client ticket **LER-1018** (Story, To Do — foundation block) · delivering ticket: **LER-2393** · build order: story 13 of 26, stage 2._

## User Story
As the pipeline, we want an automated scan that fails the build on personal-data patterns in storage keys and filename templates, so that Global DoD #11 is enforced continuously by a tool rather than asserted by a one-off volume inspection (the Railway evidence pattern, made repeatable).

## Acceptance Criteria
- Given `tools/pii-scan` (beside orphan-scan, same conventions: report / `--json` / `--quiet`, exit 1 on a finding), when run, then it walks every stored document key and the filename-template code paths and fails on personal-data patterns: any seeded/case defendant field value, DOB-shaped dates, and the defendant-field name heuristics.
- Given the tool, when it ships, then it carries self-tests the way conformance does — a deliberately leaky key fixture must fail, the compliant scheme must pass.
- Given CI, when it runs, then the scan is a step (after db:setup) and a leaky key fails the build.
- Given generation itself (LER-1166), when a would-be key fails the same rules at write time, then generation fails loudly — the tool and the write-time guard share one rule module in `libs/shared` or `tools/`, not two implementations.

## Notes & Constraints
- False-positive posture: fail closed. A storage key has no legitimate reason to resemble personal data, so aggressive patterns are correct here in a way they would not be for form content.

## Definition of Done
- Tool + self-tests + CI step delivered; write-time guard shares the rule module
- Full gate set green (now including the scan itself)

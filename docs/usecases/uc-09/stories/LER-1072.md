# LER-1072 — Page-count interpolation, gated on the approved wording

## User Story
As the declaration's renderer, we want the counted page number written into the declaration text at render time, so that the 2013 specimen's "(consisting of ___ page(s) each signed by me)" parenthetical can be honoured the moment a practitioner approves the wording — without a second engineering round.

## Acceptance Criteria
- Given the interpolation function in `libs/shared`, when given an approved wording containing the count placeholder and a count N, then it produces the declaration with N interpolated ("1 page" / "N pages" handled), and given a wording with no placeholder it returns the wording unchanged.
- Given the SHIPPED wording (which omits the parenthetical — the 24 Aug mismatch finding), when any document renders today, then the declaration is byte-identical to `MG11_DECLARATION` and nothing is interpolated: the mechanism exists, the wording decision does not move.
- Given the hash-pin discipline, when a wording change is ever approved, then constant and SHA-256 change together in one reviewable commit and the API still refuses to boot on mismatch — interpolation happens at render, never by mutating the constant.
- Given unit tests, when they run, then placeholder/no-placeholder, 0/1/N, and the shipped-wording-unchanged property are covered.

## Notes & Constraints
- Evidence for the wording question: `docs/answers/template-sourcing-evidence-2026-08.md` §3. This story must not resolve Q1 — it makes Q1's answer cheap.
- The rendered declaration is derived output; the stored draft still records only `declarationConfirmed`.

## Definition of Done

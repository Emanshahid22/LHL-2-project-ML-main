# LER-1153 — Generate PDF action, gated on a passing review

_UC-09 PDF Generation & Formatting · epic: `docs/usecases/uc-09/epic.md` · PRD: `docs/usecases/uc-09/prd.md`_

_Client ticket **LER-1153** (Story, To Do) · delivering ticket: **LER-2373** · build order: story 07 of 26, stage 2._

## User Story
As a solicitor with a reviewed form, we want a Generate PDF action available exactly when the quality check passes, so that a document can only ever be produced from a form the UC-08 gate would let through.

## Acceptance Criteria
- Given a draft whose latest server-side review passes (or which is FINALISED), when `POST /drafts/:id/pdf` is called, then a job is created, `{ jobId }` returns, and a `PDF_GENERATED` audit event records the outcome when it completes.
- Given a draft with blocking issues, when the endpoint is called — directly, without the UI — then it re-runs the UC-08 gate server-side and refuses with 409 naming the refusal; a client claim of a passing review is never trusted.
- Given the review screen and the finalised banner's UC-09 stub, when the gate passes, then the stub becomes the real Generate PDF control (with `data-testid`), showing job progress by polling `GET /pdf-jobs/:jobId`.
- Given an empty or unreviewed draft, when viewed, then the control is disabled with the reason — mirroring the review trigger's own pre-condition pattern.

## Notes & Constraints
- The gate re-run is the same engine invocation the finalise endpoint uses — one gate, two callers, no drift.
- Open question Q3 (should UC-05 format errors also gate generation?) is recorded, not resolved here.

## Definition of Done
- Delivered against the criteria; the direct-API refusal has its own check (the UC-07/08 hostile-client pattern)
- Full gate set green; every existing `data-testid` intact

# LER-1168 — Generation failure surfaces a retry

_UC-09 PDF Generation & Formatting · epic: `docs/usecases/uc-09/epic.md` · PRD: `docs/usecases/uc-09/prd.md`_

_Client ticket **LER-1168** (Story, To Do) · delivering ticket: **LER-2388** · build order: story 14 of 26, stage 2._

## User Story
As a solicitor whose generation failed, we want the failure explained with a working retry, so that a transient fault costs one click rather than a support call.

## Acceptance Criteria
- Given a failed job, when the client polls, then it receives a user-readable reason and `retryable: true`, the UI shows both, and Retry enqueues a fresh job (`PDF_RETRIED` audited) without any re-entry of form data.
- Given a retry after a transient fault (induced in a test: first render made to fail, second allowed), when it runs, then it succeeds and produces a byte-valid document.
- Given repeated failure, when it recurs, then each attempt is audited separately and the UI keeps the reason visible — no silent loop.

## Notes & Constraints
- Paired with LER-1169: retry is only trustworthy because failure provably never mutates the draft.

## Definition of Done
- Delivered against the criteria; induced-failure e2e path; full gate set green

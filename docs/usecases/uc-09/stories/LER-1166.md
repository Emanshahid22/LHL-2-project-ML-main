# LER-1166 — PII-free storage identity by construction

_UC-09 PDF Generation & Formatting · epic: `docs/usecases/uc-09/epic.md` · PRD: `docs/usecases/uc-09/prd.md`_

_Client ticket **LER-1166** (Story, To Do) · delivering ticket: **LER-2386** · build order: story 11 of 26, stage 2._

## User Story
As the storage layer, we want every stored object named from content hash and case UUID alone, so that no defendant personal data can exist in a storage key by construction rather than by review.

## Acceptance Criteria
- Given any generated document, when stored, then its key is `documents/<caseUuid|standalone>/<contentHash>.<kind>.enc` — no name, date of birth, URN, form values or any human-meaningful fragment.
- Given a draft whose values contain a known defendant name, when its document is generated in a test, then no storage key (and no path segment) contains any substring of any defendant field value.
- Given a standalone (case-less) draft, when stored, then the key uses the `standalone` segment — the scheme has no fallback that leaks.
- Given the key-derivation function, when unit-tested, then the never-contains-personal-data property is asserted over the seeded fixtures.

## Notes & Constraints
- Readable names exist only at download time (LER-1167). The scan tool (LER-1018) turns this story's property into a standing gate rather than a one-off proof.

## Definition of Done
- Delivered against the criteria; unit property tests + the e2e known-name probe; full gate set green

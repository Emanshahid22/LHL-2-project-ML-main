# LER-1015 — API-boundary enforcement

_Release 01 Auth & RBAC · epic: `../epic.md` · PRD: `../prd.md`_

_Client ticket **LER-1015** (Story, To Do) · delivering ticket: to be

## User Story
As the platform's security boundary, we want every authorisation decision
made at the API and never in the interface, so that a client-side defect
cannot expose protected material.

## Acceptance Criteria
- Given any endpoint except `GET /api/health`, when called without a
  valid session, then 401 — proven endpoint-by-endpoint (the 401 matrix
  walks every controller route).
- Given a valid session lacking the endpoint's declared capability, when
  called, then 403 naming the required level, never content (the UC-07
  message pattern) — proven by the role×endpoint matrix against PRD §5's
  table.
- Given a new endpoint added without a requirement declaration, when the
  build runs, then it FAILS (completeness check) — default-open cannot
  happen by omission.
- Given privilege-escalation attempts (a non-admin PATCHing roles/grants,
  a forged capability header, a tampered cookie), when received, then
  403/401 with no state change and no information leak.
- Given the Angular client with role-aware presentation removed entirely,
  when the API is exercised directly, then every protection above still
  holds (the UI is courtesy — the suite's direct-API discipline).

## Notes & Constraints
- The existing ownership/CaseAccess/sensitive-grant scoping stays INSIDE
  services as built; the capability layer sits in front, never replacing
  those deeper checks (defence in depth, not consolidation).

## Definition of Done
- 401 + 403 matrices green; completeness check wired into the build;
  escalation attempts covered; full battery green.

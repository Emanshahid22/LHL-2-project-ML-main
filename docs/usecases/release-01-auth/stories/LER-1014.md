## User Story
As a firm, we want platform access divided into administered roles with a
separately-assignable sensitive-material grant, so that who can do what is
a managed decision rather than an implicit default.

## Acceptance Criteria
- Given the seeded role rows (final names per ruling #1 — the ticket
  names Administrator, Senior Solicitor, Paralegal, Read-Only; D-G
  defines the capability semantics), when a user acts, then their
  capabilities resolve through the ONE shared role→capability mapping
  (unit-matrix-tested) — roles are data, renameable at ratification.
- Given the Sensitive Material Access grant, when assigned or revoked,
  then the existing UC-07/09/10 predicate follows immediately (write
  gate, render redaction, serve-time re-check, diff redaction — the
  UC-07 e2e matrix re-passes unchanged), and no role carries the grant
  automatically.
- Given an ADMIN, when they call any content endpoint (cases, drafts,
  documents, archive, exports), then 403 — user/role/grant management
  only (D-G4, separation of duties).
- Given a Senior Solicitor, when they view the advisory-bypass oversight
  listing, then acknowledgement records are visible (read-only, scoped to
  `oversight.bypasses` — ruling #9 confirms the minimum).
- Given any role or grant mutation, when it commits, then it is audited
  (USER_ROLE_CHANGED / GRANT_CHANGED) with actor and subject ids only.

## Notes & Constraints
- D-G is PROVISIONAL; the LER-1014 four-role list conflict is ruling #1
  and blocks only the seed names, not the mechanism.
- Historical audit rows keep their identity; seeded e2e fixture users per
  role join e2e/FIXTURES.md.

## Definition of Done
- Role×endpoint 403 matrix green; admin-separation test green; UC-07
  matrix re-passes; unit matrix over the shared mapping.
